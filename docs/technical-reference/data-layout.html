AOS vs SOA

Data layout choices used to balance ownership clarity and cache-friendly updates.

The codebase uses both layouts with explicit roles. Entity metadata is kept in AOS form (std::vector<Entity>), while frequently updated transform and physics state are organized in SOA form for tighter field-wise scans.

This split keeps ownership and editor-facing data simple, while letting physics and transform-heavy code iterate through contiguous columns such as position, velocity, and inverse mass. 

// src/pba/scene/world.hpp
std::vector entities_{};
TransformSOA transforms_{k_max_number_objects};

// src/pba/physics/physics_types.hpp
std::vector positions{};
std::vector velocities{};
std::vector inv_masses{};
std::vector orientations{};
std::vector inv_inertia_worlds{};

Relevant files: src/pba/scene/world_types.hpp, src/pba/physics/physics_types.hpp, src/pba/scene/world.cpp.

Practical Notes from CppCon 2025

Following the practical DoD guidance from "More Speed & Simplicity", relationships in hot data paths are modeled as compact handles/indices instead of owning pointers. 

// src/pba/scene/world.hpp
std::unordered_map id_to_index_{};

// src/pba/physics/physics_types.hpp
struct BodyHandle {
    u32 index{};
};

This keeps state relocatable and layout control explicit, while higher-level systems can still expose object-style APIs at module boundaries.
